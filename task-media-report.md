# Доставка медиа в Битрикс24 и честный отказ вместо тишины

Ветка `feat/bitrix-media`, база `bb40cf5`.

## Зачем

Живая проверка 08.08: на «сделай кружочек» Ава сгенерировала видео, а
`BitrixChannel.send()` отправлял только `message.text` — видео молча
выбрасывалось. Человек ждал впустую и не знал почему.

## Что сделано

### 1. Доставка файла в чат портала

`BitrixClient.sendFile()` — три вызова портала в единственно рабочем порядке:

| Вызов | Что даёт |
|---|---|
| `im.disk.folder.get` (`CHAT_ID`) | номер папки чата на Диске |
| `disk.folder.uploadfile` (`id`, `data.NAME`, `fileContent: [имя, base64]`) | файл на Диске, его `ID` |
| `im.disk.file.commit` (`CHAT_ID`, `DISK_ID`, `MESSAGE`) | файл появляется в чате |

Текст ответа уезжает **вместе с файлом** — в `MESSAGE` вызова `commit`.
Одно сообщение, а не два, которые могут выполниться наполовину.

`generateUniqueName: "Y"` — два кружочка подряд оба называются `krug.mp4`,
пусть портал хранит оба.

### 2. Откуда берётся `CHAT_ID`

- `chat42` → `42`, прямо из `dialogId`, без похода в портал;
- личный диалог (`dialogId` — номер человека, `17`) → один лишний вызов
  `im.dialog.get` с `DIALOG_ID`, в ответе `id` — номер чата.

Почему так: у `im.disk.folder.get` параметр `CHAT_ID` — число, а форма
`DIALOG_ID` документирована **только** для вида `chatXXX`. `im.dialog.get`
принимает и голый номер пользователя и отдаёт `id` чата. Оба вида закрыты
тестами.

### 3. Честный отказ вместо тишины

Любая причина, по которой файл не уехал, кончается **одним** сообщением,
где есть и ответ Авы, и объяснение по-русски:

| Причина | Что слышит человек |
|---|---|
| портал отказал (в т.ч. нет права `disk`) | «Видео я записала, но отправить его в Битрикс не получилось — здесь я пока умею только текстом.» |
| файла нет на диске / не скачался | «…но сам файл до меня не доехал — отправить его не получилось. Оставляю ответ текстом.» |
| больше 20 МБ | «…но получилось слишком тяжело для Битрикса (больше 20 МБ)…» |
| ссылка непонятного вида | «…но такое вложение я в Битрикс отправлять не умею…» |

Начало фразы согласовано с видом медиа: «Видео я записала» / «Голосовое я
записала» / «Картинку я сделала» / «Файл я подготовила».

Кода ошибки и английского в чат не попадает. Код портала и HTTP уходят
в журнал (`console.warn`) — там они и нужны.

### 4. Что уже работало — работает так же

Нет `mediaPath`/`mediaUrl` → ровно прежний путь: один `imbot.message.add`.
Проверено тестом-регрессией (никаких файловых вызовов вообще).

### 5. Размер и виды ссылок

Предел **20 МБ** на сырые байты. Локальный файл проверяется по `stat` **до**
чтения — переростка в память не тянем. `data:`-ссылка и `http(s)`-ссылка
(что отдают `image_gen`/`selfie`) проверяются и по `content-length`, и по
факту после чтения.

### 6. Секреты

`client.ts` переведён на общий `call(method, payload)` — прежняя дисциплина
сохранена: наружу только вид ошибки, HTTP-код и код ошибки портала.
`error_description` не печатается никогда. Порядок проверки поменялся в одном
месте: код ошибки портала теперь важнее статуса, потому что отсутствие права
`disk` приходит как `HTTP 401 insufficient_scope`, а один «HTTP 401» читается
как «умер токен» и уводит отладку не туда.

## Проверка честности (ломал по одному месту, возвращал сразу)

| Что ломал | Что упало |
|---|---|
| `deliver()` → снова только `message.text` (молчаливый выброс) | **10 из 13**, включая все тесты на честный отказ |
| отказ портала проглатывается (текст без объяснения) | тест «нет права `disk`» |
| убран предел размера | тест «файл больше предела» |
| `chatNN` больше не разбирается | 4 теста, включая «CHAT_ID прямо из dialogId» |
| `error_description` подмешан в текст ошибки | оба теста на утечку токенов |
| `MESSAGE` в `im.disk.file.commit` затёрт | «текст не теряется» и вебхук-тест |

Первый прогон вскрыл собственную халтуру: тесты «файла нет на диске» и
«непонятная ссылка» **проходили и при молчаливом выбросе** — проверяли лишь
наличие кириллицы. Усилены до проверки самого объяснения, после чего падают
как положено.

Дерево после всех проверок чистое, изменения возвращены.

## Сомнения и что не проверено без живого портала

1. **Личный диалог через `im.dialog.get` — не замерен.** Метод и поле `id`
   взяты из документации Битрикса, право `im` у приложения есть. На боевом
   портале вызов не выполнялся. Если портал ответит иначе — сработает честный
   отказ, молчания не будет. Это важно, потому что Ава по спецификации
   отвечает **только в личных диалогах**: именно этот путь и будет рабочим.
2. **`disk.folder.uploadfile` требует право `disk`, которого у приложения
   нет** (замер: `HTTP 401 insufficient_scope`). Пока право не выдано, каждая
   отправка медиа кончается вежливым отказом в чат. Как только владелец его
   добавит — путь заработает без правок кода.
3. **`DISK_ID` против `UPLOAD_ID`.** Отдаём `DISK_ID` — номер файла, уже
   лежащего на Диске (то, что вернул `uploadfile`). `UPLOAD_ID` — для другого
   способа загрузки. Живьём не проверено.
4. **Форма ответа `im.disk.folder.get`.** Документация обещает `result.ID`,
   старые сборки отдавали голое число. Разбор терпит оба вида плюс `id` —
   но какой именно придёт с боевого портала, неизвестно.
5. **Голосовые.** Уедут как обычный файл (`.ogg`/`.mp3`), «голосовым
   сообщением» в интерфейсе Битрикса не станут — отдельного механизма у
   `im.disk.file.commit` нет. Кружочек-видео тоже приедет обычным видео:
   аналога телеграмного `video note` в портале нет.
6. **Кириллица в имени файла** до портала доезжает как есть; на боевом
   не проверялось.
