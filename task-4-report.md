# Задача 4 — клиент ходит токеном приложения

## Что сделано

`src/channels/bitrix/client.ts`

- `BitrixClient` теперь принимает объект настроек: источник токенов
  (`BitrixTokenSource` — подмножество `BitrixTokenStore`: `load` / `save` /
  `isExpired`), `botId`, `clientId`, `clientSecret`, а также подменяемые
  `fetchImpl` и `refreshImpl` (шов для тестов).
- Адрес запроса строится из домена портала в хранилище:
  `https://<domain>/rest/imbot.message.add.json`. Вебхук владельца больше не
  участвует в отправке.
- `auth=<access_token>` уходит **телом** запроса вместе с `BOT_ID`,
  `DIALOG_ID`, `MESSAGE` — строка адреса оседает в журналах промежуточных
  узлов, тело нет.
- Обновление токенов:
  1. перед запросом — `isExpired`: просроченные обновляются заранее, не
     дожидаясь отказа портала;
  2. если портал всё же ответил `expired_token` — обновление **один раз** и
     ровно один повтор; повторный `expired_token` → исключение. Цикла нет по
     построению: два вызова `attempt`, между ними одно `refresh`.
- Свежая пара сразу пишется в хранилище; неудача записи — не «тихая»:
  исключение с кодом errno (старый refresh-токен уже потрачен, потерять новую
  пару значит запереть приложение).
- Пустое хранилище → исключение по-русски: «приложение не установлено —
  токены портала не найдены», запрос не уходит вовсе.
- Секреты наружу не идут: сеть — только `err.name`, HTTP — только код,
  портал — только код ошибки (без `error_description`, он эхом возвращает
  данные запроса), обновление — только `err.name`, запись — только errno.
- Сохранено как было: обрезка до 8000 знаков с защитой суррогатных пар,
  `BOT_ID`, проверка `data.error` при HTTP 200. Тело ответа теперь читается и
  при не-2xx — иначе `expired_token` (приходит как 401) не распознать; если
  тело не JSON, а ответ не 2xx, сообщение прежнее — про код HTTP.

`src/channels/bitrix/index.ts` — одна строка на месте вызова конструктора
(иначе `typecheck` красный): клиент собирается из `tokenStore` и
`client_id` / `client_secret` из настроек; без хранилища клиента нет —
канал стартует и принимает события, а о проблеме сообщает первая же отправка.
Остальное в файле не тронуто, `src/index.ts` не тронут вовсе.

## Тесты

`test/channels/bitrix-client.test.ts` — 8 новых проверок (домен и `auth`;
токен телом, не в адресе; упреждающее обновление; обновление один раз +
повтор; отказ после второго `expired_token` со счётчиком; сохранение свежей
пары; пустое хранилище; отсутствие секретов на **всех** путях отказа —
сеть, HTTP, не-JSON, ошибка портала, сбой обновления на обоих путях, сбой
записи, «не установлено»). Прежние проверки обрезки, `BOT_ID` и `data.error`
переписаны под новый конструктор.

Итог: **1011 passed | 84 skipped | 0 failed** (база 1005 + 6 чистого
прироста), `npm run typecheck` — 0.

Перед реализацией тесты запускались на старом коде: 11 из 15 падали.

## Проверка честности

Ломал по одному месту, после каждого прогона сразу `git checkout --`:

| Что сломано | Упало |
|---|---|
| Снят предел «обновлять один раз» (`while` по `expired`) | процесс съел кучу и умер по OOM — цикл поймали, но грязно |
| Вместо предела — второе обновление (ограниченный вариант) | 3 теста, включая «gives up after one refresh» по счётчику |
| Токен перенесён в строку адреса | 4 теста, включая «puts the token in the body, never in the URL» |
| Убрано упреждающее обновление | «refreshes an already-expired token BEFORE sending» + проверка секретов |
| В ошибке обновления `err.message` вместо `err.name` | ровно «keeps tokens and the client secret out of every failure message» |
| Убран отказ при пустом хранилище | ровно «refuses to send when the application is not installed» |

Каждый раз падал нужный тест. Бесполезных не нашлось.

## Сомнения

- `client_id` / `client_secret` берутся из `config` канала — ключей
  `client_id` и `client_secret` в настройках пока нет: их заводит другая
  задача этапа. Пока там пусто, обновление токена отобьёт портал, и это
  видно в тексте ошибки (код портала), а не молча.
- Сбой записи свежей пары на диск роняет отправку сообщения, хотя токен в
  памяти рабочий. Считаю это правильным: пара уже выдана, старый
  refresh-токен потрачен, и молчаливое продолжение оставит приложение
  запертым к следующему запуску без единого следа.
- Живой проверки на портале не было — только моки; она в «Сдаче этапа».
