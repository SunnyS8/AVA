# Переустановка приложения от «Администрация Офис», 10.08.2026

Продолжение `2026-08-08-bitrix-app-deploy.md`. Это **порядок работ на сегодня**,
замеры вписываются по ходу — таблицы внизу пока пустые.

## Зачем

Приложение сейчас установлено личным профилем, и портал выдал токены **этому
профилю**. Значит Ава ходит в портал его правами и видит то же, что он, включая
его переписку. Нужно, чтобы приложение принадлежало служебному профилю
**«Администрация Офис» (ID 238)** — тому самому, от чьего имени спека (§15б)
велит создавать задачи.

Приложение переустанавливается целиком: новое приложение — это новые
`client_id`/`client_secret`, новый `application_token` и **новый бот**. Старый
бот `442` принадлежит старому приложению и уходит вместе с ним.

## Окно молчания

Оно неизбежно, и его надо назвать вслух. Пара ключей в настройках одна, файл
токенов один: как только в конфиг лягут ключи нового приложения, обновить
токены старого нечем — старый бот замолчит не позже чем через час (когда
истечёт текущий access-токен), а после установки нового — сразу.

Отсюда порядок ниже: шаги 3–8 идут **подряд, за один присест**, и старое
приложение снимается только после того, как новый бот ответил живому человеку.
Ожидаемое окно — минуты между установкой и вписыванием нового `bot_id`.

## Что нужно от владельца

1. Доступ в портал **под профилем «Администрация Офис»** — именно под ним
   создаётся и устанавливается приложение.
2. Нажатия «Установить» и «Удалить» на странице приложения.

## Порядок работ

### 0. Бэкапы (сервер)

```bash
sudo -u ava cp /home/ava/.betsy/config.yaml \
              /home/ava/.betsy/config.yaml.bak-$(date +%F-%H%M)
sudo -u ava cp /home/ava/.betsy/bitrix-tokens.json \
              /home/ava/.betsy/bitrix-tokens.json.bak-$(date +%F-%H%M)
```

Файл токенов **не удалять**. Установка с того же портала проходит проверку
`memberId` и перезаписывает файл сама (`src/channels/bitrix/index.ts`,
`handleInstall`); а пустое хранилище — это открытое окно захвата, известная
слабость №1 из отчёта 08.08.

### 0б. Доставить скрипт проверки на сервер

`deploy/2.sh` кладёт в `/opt/ava` только `dist/` и `package.json` — папка
`scripts/` туда не попадает, её копировали руками. Новый `check-bitrix.mjs`
нужно положить рядом с уже лежащим там `register-bitrix-bot.mjs`:

```bash
scp scripts/check-bitrix.mjs root@83.222.26.241:/opt/ava/scripts/
```

Проверить, что на сервере есть и аватарка — скрипт регистрации берёт её из
`/opt/ava/assets/ava-avatar.jpg` и без неё зарегистрирует бота безликим:

```bash
ssh root@83.222.26.241 'ls -l /opt/ava/assets/ava-avatar.jpg /opt/ava/scripts/'
```

### 1. Создать приложение (портал, под «Администрация Офис»)

Разработчикам → Другое → Локальное приложение.

| Поле | Значение |
|---|---|
| Тип | использующее только API (серверное) |
| Путь обработчика | `https://83.222.26.241.sslip.io/bitrix/` |
| Путь для первоначальной установки | `https://83.222.26.241.sslip.io/bitrix/` |
| Права | `imbot`, `im`, `user`, `department`, `task`, `tasks_extended`, `calendar` |

Права выдаём **все семь сразу**, включая три для задач и календаря: они
понадобятся следующему этапу (спека §15б), а добавление права позже требует
переустановки приложения — то есть повторения всей этой процедуры.

**«Установить» пока НЕ нажимать.** Со страницы забрать код (`client_id`) и ключ
(`client_secret`).

### 2. Ключи в настройки (сервер)

В `/home/ava/.betsy/config.yaml`, раздел `bitrix`: заменить `client_id` и
`client_secret`. `bot_id` пока **не трогать** — старый бот доживает свои минуты
и пусть отвечает.

```bash
sudo systemctl restart ava
sudo journalctl -u ava -n 30 --no-pager
```

С этого момента окно молчания открыто — дальше без пауз.

### 3. Установка (портал)

Нажать «Установить». В журнале ждём:

```
bitrix: application installed, tokens saved
```

Проверить, что файл действительно переписан и остался закрытым:

```bash
sudo ls -l /home/ava/.betsy/bitrix-tokens.json   # свежая метка времени, права 600
```

Тишина в журнале означает, что событие не долетело. `ONAPPINSTALL`
**одноразовое**: повторно портал его не пришлёт — снять приложение и поставить
заново.

### 4. Первая проверка (сервер)

```bash
sudo -u ava HOME=/home/ava node /opt/ava/scripts/check-bitrix.mjs
```

Что должно быть видно:

- **права** — все семь;
- **токены выданы профилю ID 238** — ради этого всё и затевалось;
- бот — ещё не зарегистрирован, это ожидаемо на этом шаге.

Одинокое `app` в правах означает не «права отобрали», а «спросили не у портала,
а у сервера авторизации» — грабли 08.08, скрипт про них напоминает сам.

### 5. Регистрация бота (сервер)

```bash
sudo -u ava HOME=/home/ava node /opt/ava/scripts/register-bitrix-bot.mjs
```

Скрипт регистрирует бота с `CODE: "ava"` и ставит аватарку из
`assets/ava-avatar.jpg`. **Аватарка задаётся только при регистрации** —
`imbot.update` отвечает «принято» и не делает ничего (замер 08.08). Нет
аватарки — только перерегистрация.

Прошлый живой бот был `442` с `CODE=ava_sis`, потому что в старом приложении код
`ava` уже занимал бот `440`. Новое приложение — новый владелец кодов, и `ava`
должен быть свободен. Если портал всё же ответит про занятый код, поменять
`CODE` в скрипте на `ava_sis` и повторить.

Ответ `expired_token` — перезапустить службу (обновит токены) и повторить.

### 6. `bot_id` в настройки (сервер)

Вписать напечатанный `BOT_ID` в `bitrix.bot_id`, затем:

```bash
sudo systemctl restart ava
sudo journalctl -u ava -n 30 --no-pager
```

Ждём: «Канал Битрикс поднят полностью: приложение установлено, бот
зарегистрирован».

### 7. Вторая проверка (сервер)

```bash
sudo -u ava HOME=/home/ava BITRIX_BOT_ID=<новый> node /opt/ava/scripts/check-bitrix.mjs
```

Теперь всё должно быть зелёным, включая аватарку у бота и совпадение `bot_id` из
настроек со списком ботов приложения.

### 8. Живая проверка (портал)

1. Написать боту в портале — приходит ответ **моделью**, а не заглушкой
   «что-то у меня зависло» (заглушка означает, что отвалился прокси, см. отчёт
   08.08).
2. Попросить прочитать файл на сервере — приходит вежливый отказ.
3. Голосовое или кружочек тому, кто есть в списках, — приходит.

### 9. Снять старое приложение (портал)

**Только после успешной живой проверки.** Вместе с приложением уходит бот `442`;
сотрудники, у кого он остался в списке чатов, увидят нового.

### 10. Через час (сервер)

Первое обновление токена — тот самый момент, на котором 08.08 всё сломалось:
домен портала подменялся сервером авторизации, и отправка падала с `404`.

```bash
sudo journalctl -u ava --since '1 hour ago' --no-pager | grep -iE '404|ERROR_METHOD_NOT_FOUND|refresh'
sudo -u ava HOME=/home/ava node /opt/ava/scripts/check-bitrix.mjs
```

Регрессия закрыта тестом (`45ca935`), но живая проверка здесь стоит одной
команды.

## Если пошло не так

| Симптом | Что это | Что делать |
|---|---|---|
| В журнале нет «application installed» | Событие установки не долетело | Снять приложение в портале, поставить заново — повторно оно не придёт |
| События отбиваются `401` | `application_token` в файле не тот, то есть установка не завершилась | То же: снять и поставить заново |
| Права: одинокое `app` | Запрос ушёл не в портал | Проверить `domain` в файле токенов — там должен быть портал, не `oauth.bitrix.info` |
| `register` → `expired_token` | Токен протух за время работы | `systemctl restart ava`, повторить |
| `register` → `HTTP 400 error 500` | Портал разбирает пустое поле как дату | Уже исправлено (`f34e46e`); если вернулось — искать пустые поля в `PROPERTIES` |
| Ава отвечает «что-то у меня зависло» | Модель недоступна: прокси или гео-блок | `journalctl` → `Engine error: 403` (гео-блок) или `LLM request through proxy failed` (прокси) |
| Бот зарегистрирован без аватарки | Файл `assets/ava-avatar.jpg` не прочитался | Только перерегистрация бота — `imbot.update` аватарку не меняет |

## Ожидания, которые проверяются именно здесь

Отделяю от фактов: ниже — то, что следует из устройства портала и кода, но
живым замером **ещё не подтверждено**. Если хоть одно не сойдётся, это меняет
порядок работ, поэтому шаги 4 и 7 стоят там, где стоят.

1. `user.current`, вызванный токеном приложения, отвечает профилем, который
   приложение установил. Отсюда и способ убедиться, что Ава ходит служебным
   профилем, а не личным.
2. Код бота (`CODE`) уникален в пределах приложения, а не портала — поэтому в
   новом приложении `ava` свободен.
3. Снятие старого приложения уносит его бота `442`.

## Что это не закрывает

Из бэклога отчёта 08.08 ничего: секретный сегмент в пути обработчика, поле
`portal_domain` вместо вводящего в заблуждение `webhook_url`, кэш ключа
приложения. Переустановка — удобный момент для секретного сегмента (адрес
обработчика всё равно вводится заново), но менять два условия сразу в живом
переходе не стоит: сломается — не поймём, что именно.
