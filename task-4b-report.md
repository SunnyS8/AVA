# Задача 4б — хранилище токенов и ключ приложения

Ветка `feat/bitrix-app`, коммит `7fd95f9` (от `797b2a0`).

## Что сделано

### 1. Хранилище токенов в точке запуска

`src/channels/bitrix/tokens.ts` — новая фабрика `createBitrixTokenStore()`:
файл `bitrix-tokens.json` в каталоге конфига, который возвращает
`getConfigDir()` (`~/.betsy`). Свой способ определения каталога не заводился —
переиспользован тот, которым конфиг уже пользуется.

`src/index.ts` создаёт канал как `new BitrixChannel({ tokenStore:
createBitrixTokenStore() })`. До этого хранилища не было вовсе: `ONAPPINSTALL`
с живого портала уходил в ветку «хранилище не настроено», и токены установки
терялись без следа.

Поле `filePath` у `BitrixTokenStore` стало `readonly` (было `private`) — чтобы
тест мог проверить сам путь, а не только его последствия.

### 2. Ключи приложения в настройках

`src/core/config.ts`, раздел `bitrix`: добавлены `client_id` и `client_secret`
(`z.string().optional()`). Optional — чтобы настройка «только вебхук» по-прежнему
разбиралась; обязательность проверяется там, где ключи действительно нужны.

`BitrixChannel.start()`: если есть хранилище, но ключей нет — исключение
по-русски («не заданы client_id и client_secret … впишите их в раздел bitrix
конфига»). `src/index.ts` ловит его и печатает одну внятную строку владельцу.
Отказ сразу, а не через час: без ключей клиент не сможет обменять refresh-токен,
и канал проработал бы ровно до истечения первого access-токена.

Секреты: в журнал не попадают (клиент и `refreshTokens` и раньше не печатали ни
токенов, ни `client_secret`; регрессионный тест на журнал в
`bitrix-install.test.ts` держит это), в `betsy.config.yaml.example` добавлен
закомментированный раздел `bitrix` только с заглушками.

### 3. `application_token` из установки

- `BitrixTokens.applicationToken?: string` — **необязательное** поле, в
  `REQUIRED_FIELDS` не входит: старый файл токенов, написанный до этого поля,
  обязан читаться, иначе он выглядит как «приложение не установлено».
- `handleInstall` → `saveInstall` кладёт `install.applicationToken` вместе с
  токенами. Портал выдаёт этот ключ один раз, внутри самого события установки, и
  больше нигде его не показывает.
- Сверка событий: `expectedApplicationToken()` — сохранённый ключ, а если его
  нет, значение из конфига. Сохранённый выигрывает: он и есть тот, которым
  портал подписывает события. Конфиг остаётся путём для вебхука и ручной
  настройки. Читается с диска на каждое событие (файл маленький и локальный), а
  не кэшируется — переустановка должна вступать в силу сразу, а не после
  перезапуска.

### Тонкое место — обновление токенов

`refreshTokens` возвращает свежую пару **без** `applicationToken`: портал при
обновлении его не присылает. Наивное `save(fresh)` стёрло бы ключ через час
после установки, и Ава молча перестала бы принимать события — «работало и
сломалось само». В `BitrixClient.refresh()` ключ переносится явно:

```ts
const merged: BitrixTokens = { ...fresh, applicationToken: tokens.applicationToken };
```

Мержится в клиенте, а не внутри `BitrixTokenStore.save()`: сделай это хранилище,
и ошибка «клиент теряет ключ» была бы замаскирована для любого другого
хранилища (в том числе в тестах).

## Тесты

Новый файл `test/channels/bitrix-app-token.test.ts` — 9 тестов:

1. путь хранилища берётся из каталога конфига (`getConfigDir()`);
2. `src/index.ts` действительно передаёт хранилище в канал;
3. `client_id`/`client_secret` разбираются схемой конфига;
4. без них — отказ старта с русским текстом;
5. `application_token` из установки сохраняется;
6. события сверяются с сохранённым ключом, а значение из конфига после
   установки отбивается (401);
7. сохранённого нет — берётся из конфига;
8. старый файл токенов без `applicationToken` читается;
9. **обновление токенов не теряет `applicationToken`**.

Итог: `npm run test` — **1020 passed | 84 skipped | 0 failed** (было 1011
passed), `npm run typecheck` — 0.

## Проверка честности

Ломал по одному месту, после каждого прогона возвращал `git checkout -- <файл>`:

| Поломка | Упавший тест |
|---|---|
| `refresh` сохраняет `fresh` вместо `merged` | обновление токенов не теряет ключ |
| в `src/index.ts` убран `tokenStore` | канал в точке запуска получает хранилище |
| `saveInstall` не пишет `applicationToken` | ключ сохраняется; сверка с сохранённым |
| сверка снова по `this.applicationToken` | сверка с сохранённым, а не с конфигом |
| из схемы убраны `client_id`/`client_secret` | разбор ключей схемой конфига |
| `applicationToken` внесён в `REQUIRED_FIELDS` | старый файл токенов читается |
| в `start()` снята проверка ключей | отказ старта с русским текстом |
| убран фолбэк на конфиг | сохранённого нет → берётся из конфига |

Все восемь падали ровно на своём тесте. После восстановления — полный прогон
зелёный, `git status --short` пуст.

## Сомнения

- **Тест «точка запуска получает хранилище» читает исходник `src/index.ts`
  регуляркой.** `src/index.ts` вызывает `main()` прямо при импорте, поэтому
  импортировать его в тест нельзя, а вынос всей проводки канала в отдельную
  функцию — отдельный рефакторинг, выходящий за рамки задачи. Проверка узкая
  (в вызове `new BitrixChannel(` есть `tokenStore`) и падает ровно на нужной
  поломке, но она чувствительна к переформатированию этого вызова.
- **`expectedApplicationToken()` читает файл на каждое событие.** На нагрузке
  живого портала это нормально (мелкий локальный файл), но если поток событий
  вырастет — стоит кэшировать с инвалидацией по mtime.
- **`application_token` в конфиге остаётся условием старта канала**
  (`src/index.ts` требует `webhook_url && application_token && bot_id`). Для
  установки приложения он, строго говоря, больше не нужен — ключ приезжает с
  установкой. Не трогал: это меняет условия запуска канала и тянет за собой
  проверку сценария «конфиг без application_token», которого в задаче нет.
  Кандидат в следующую задачу.
- Живой портал не проверялся — только тесты; это задача этапа приёмки.
